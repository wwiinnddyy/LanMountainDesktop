# 桌面宿主

宿主（`LanMountainDesktop`）是长期驻留的主进程：桌面网格、托盘、设置窗口、组件库与 AirApp 运行时都在这里。本文只讲**进程级生命周期**——启动顺序、启动阶段上报、关闭协调、窗口与托盘归属。

- 启动器侧流程：[启动器系统](02-启动器系统.md)
- AirApp 运行时：[AirApp 运行时](04-AirApp运行时.md)
- 组件与设置：[组件系统](05-组件系统.md)、[设置系统](06-设置系统.md)

代码位置：`desktop/LanMountainDesktop/`（入口 `Program.cs`、应用级 `App.axaml.cs`、外壳 `DesktopShellHost.cs`）。

最后核对：2026-11-14。

---

## 1. 关键结论：宿主自己不做单实例

**宿主没有单实例机制。** `DesktopShellHost` 注册的 activation listener 是一个空实现（`static () => { }`）。

"不要开第二个桌面"这件事完全由**启动器**负责：

- 启动器在启动宿主前先探测已有宿主：连公共 IPC 调 `GetShellStatusAsync`，判据是 `PublicIpcReady && ProcessId > 0`（3s 超时）。
- 命中后按设置里的多实例行为分派：`RestartApp` / `OpenDesktopSilently` / `PromptOnly` / `NotifyAndOpenDesktop`。
- "把参数交给已有实例"实际上是对它发 IPC 命令（激活主窗口 / 重启），**不是命令行转发**。

所以直接双击 `LanMountainDesktop.exe`（绕过启动器）是可以起第二个宿主的。安装器另有自己的命名互斥锁，与宿主/启动器无关。

## 2. 进程入口

`Program.Main` 的顺序：

```
AppLogger.Initialize
→ AppDataPathProvider.Initialize(args)
→ DevAirAppOptions.Parse(args)
→ RegisterGlobalExceptionLogging
→ DesktopBootstrap.InitializeStartupServices(...)
→ StartupDiagnosticsService.Run(args)
→ 读渲染模式 → BuildAvaloniaApp(renderMode).StartWithClassicDesktopLifetime(args)
```

两条韧性措施：

- **渲染失败重试**：疑似渲染问题时用软件渲染再试一次，可用 `LAN_DESKTOP_DISABLE_RENDER_RETRY` 关闭。
- **崩溃转储**：未处理异常时写转储，供事后分析。

## 3. 启动顺序

`App.Initialize`：

```
AvaloniaXamlLoader.Load
→ ApplyThemeFromSettings
→ ApplyCurrentCultureFromSettings
→ EnsureSettingsWindowService
→ EnsureWeatherLocationRefreshService
→ EnsureNotificationService
```

`App.OnFrameworkInitializationCompleted`：

```
LinuxDesktopEntryInstaller.EnsureInstalled
→ InitializePublicIpc                      ← 起公共 IPC 主机
→ InitializeLauncherIpcAsync（fire-and-forget）
→ DesktopBootstrap.InitializeApplication(this, InitializeDesktopShell)
→（Windows）DesktopPanelManagerServiceFactory.Initialize
```

`DesktopShellHost.Initialize` 内部顺序：**AirApp 运行时 → 托盘 → `desktop.Exit` 钩子 → activation listener → 创建主窗口 → 天气刷新**。

注意 AirApp 运行时排在托盘之前：托盘先就绪没有意义，因为组件的可见前提是运行时已加载。

## 4. 启动阶段上报

阶段枚举 `StartupStage` 定义在 `core/LanMountainDesktop.Core/Launcher/LauncherIpc.cs`（11 个取值）。宿主通过 `ReportStartupProgress` 上报，启动器据此显示 Splash 文案与判定成功：

| 阶段 | 进度 | 上报点 |
|---|---|---|
| `Initializing` | 10 | `App.axaml.cs` |
| `LoadingSettings` | 20 | `App.axaml.cs` |
| `LoadingAirApps` | 30 → 35 | 开始 / 完成（含失败降级） |
| `InitializingUI` | 60 | `App.axaml.cs` |
| `TrayReady` | 75 | 托盘就绪 |
| `ActivationFailed` | 80 | 激活失败 |
| `ShellInitialized` | 85 | 外壳就绪 |
| `BackgroundReady` | 95 | 后台就绪 |
| `DesktopVisible` | 100 | 桌面可见 |
| `Ready` | 100 | 可交互 |
| `ActivationRedirected` | — | 已激活到现有实例（由启动器判定） |

两个机制保证上报不丢：

- **IPC 未就绪时先缓冲**：进度消息排队，IPC 就绪后 `FlushPendingLauncherProgressAsync` 一次性冲刷。
- **心跳 5s**：保活直到主窗口打开或关闭开始，让启动器能区分"慢"和"死"。

主窗口 `Opened` 之后收尾：停 `LoadingStateReporter`，上报 `Ready` / `DesktopVisible`。

## 5. 关闭协调

```
TrySubmitShutdown(request)
  → HostShutdownGate.Submit
       首次提交胜出 → 真正执行
       重复且同模式 → 承认但不重复执行
       冲突模式     → 拒绝
  → PerformExitCleanup
  → 强制结束看门狗：8 秒后 Environment.Exit(0)（Interlocked 保证只调度一次）
```

`PerformExitCleanup` 的顺序（顺序本身是设计的一部分）：

```
停看门狗 → 退订设置/主题事件 → telemetry 会话结束 → Update.TryApplyOnExit
→ AirAppRuntime.Dispose → PublicIpcHostService.Dispose → 设置窗口 Close
→ SettingsPageRegistry.Dispose → 关组件库窗口 → DesktopPanelManagerService.Shutdown
→ 录音/学习分析共享服务释放 → DisposeTrayIcon → crash telemetry 捕获/释放
```

另一条等价入口是 Avalonia 的 `desktop.Exit` → `OnDesktopLifetimeExit`（同样走 `PerformExitCleanup` + 调度强制结束）。

关闭期间的统一判据是 `IsShutdownInProgress`——需要判"现在是不是在退出"的地方都用它，不要各自标记。

**8 秒预算是硬约束**：任何挂在关闭路径上的清理都要短。AirApp 的 `OnStoppingAsync` 与 hosted service 停止都在这条预算内（见 [AirApp 运行时](04-AirApp运行时.md) 第 2 节）。

## 6. 窗口与托盘归属

| 界面 | 归属服务 |
|---|---|
| 托盘图标 | `DesktopTrayService`（含看门狗与恢复） |
| 主窗口 | `MainWindow`，由宿主的 `CreateAndAssignMainWindow` 管理生命周期 |
| 设置窗口 | `SettingsWindowService`（`ISettingsWindowService`） |
| 组件编辑器窗口 | `ComponentEditorWindowService` |
| 桌面板组件库 | `DesktopPanelComponentLibraryWindow`（宿主级窗口）+ 主窗口内嵌组件库 |

## 7. 与启动器的边界

- **宿主自知来源**：`LauncherRuntimeMetadata.GetLaunchSource(args)` 读 `--launch-source`；词表 `LauncherLaunchSources{normal, restart, postinstall, plugin-install, debug-preview}` 与选项名常量都收口在 `core/.../Launcher/LauncherIpc.cs`。
- **重启委派**：宿主重启时不自己拉新进程，而是追加 `--launch-source=restart --restart-presentation=...` 交给启动器，呈现模式为 minimized / tray / foreground。
- **数据根**：由启动器通过 `--data-root` 与 `LMD_DATA_ROOT` 传入，宿主只负责读取。
- **开发模式差异**：`DevAirAppOptions.Parse` 识别 `--dev-mode` / `-dev`、`--dev-airapp` / `-dp`、`--hot-reload` / `-hr` 以及 `LMD_DEV_AIRAPP` / `LMD_DEV_MODE`；`IsDevModeEnabled` 为假时设置页里的 `Dev` 分类不出现。

---

## 8. 已知薄弱点

| 现象 | 说明 |
|---|---|
| 直接启动宿主可起多实例 | 单实例由启动器保证，绕过启动器即绕过该保证 |
| activation listener 是空实现 | 名字暗示"响应外部激活请求"，实际什么都不做；激活靠启动器发 IPC 命令 |
| 两套组件面并存 | 桌面网格与 Windows 桌面板各有一套布局持久化，改动时容易只改一侧（见 [组件系统](05-组件系统.md)） |
| 关闭预算 8 秒 | 清理逻辑变重就得重新审视这条预算，而不是让它超时被杀 |
