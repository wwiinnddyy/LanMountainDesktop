# 启动器系统

启动器（`LanMountainDesktop.Launcher`）是**短生命周期**进程：负责把桌面宿主安全地拉起来，交接到位后就退出。它不承载桌面组件、不承载窗口轻应用，也不在交接后以透明/后台窗口驻留。

- 结构与进程拓扑：[整体架构](01-整体架构.md)
- 宿主侧生命周期：[桌面宿主](03-桌面宿主.md)

代码位置：`desktop/LanMountainDesktop.Launcher/`；部署标记与目录约定的唯一权威是 `core/LanMountainDesktop.Core/Deployment/`。

最后核对：2026-11-14。

---

## 1. 模块地图

| 模块 | 文件 | 职责 |
|---|---|---|
| 进程入口 | `Program.cs` | 全局异常处理、解析参数，分流三条路径：旧插件安装 / CLI / GUI |
| 参数解析 | `CommandContext.cs` | 命令词与选项解析，判定 `IsGuiCommand` / `IsDebugMode` / `LaunchSource` |
| 顶层协调 | `Shell/LauncherGuiCoordinator.cs` | 登记启动所有权、启动协调 IPC、失败重试循环、成功后的 Runtime 交接 |
| DI 装配 | `Shell/LauncherServiceRegistration.cs`、`Shell/LauncherCompositionRoot.cs` | 注册 5 个 `ILaunchPhase` 与 `LaunchPipeline` |
| 编排 | `Shell/LauncherOrchestrator.cs` | 评估 OOBE、创建 Splash、挂 IPC 上报、构造并运行管线 |
| 管线 | `Startup/LaunchPipeline.cs` | 顺序执行阶段，直到某阶段返回 `Completed` 短路 |
| 阶段 | `Startup/Phases/*.cs` | 见第 2 节 |
| 宿主启动 | `Startup/HostLaunchService.cs` | 定位宿主 exe、预启动 Runtime、按 Direct→ShellExecute 尝试、捕获 stderr |
| 启动监控 | `Startup/HostStartupMonitor.cs` | 等待成功判据、处理退出与软/硬超时 |
| 成功判定 | `Startup/StartupSuccessTracker.cs` | 按成功策略判定是否达成 |
| 尝试状态 | `Startup/StartupAttemptRegistry.cs` | state 文件 + 命名互斥锁 + 陈旧清理 |
| 多实例 | `Startup/HostActivationPolicy.cs`、`Startup/ExistingHostProbe.cs` | 已有宿主探测与多实例行为 |
| 部署 | `Deployment/DeploymentLocator.cs` | 枚举、排序、清理部署目录 |
| 启动计划 | `Deployment/HostLaunchPlan.cs` | 组装转发给宿主的参数与环境变量 |
| OOBE | `Oobe/*` | 状态判定、欢迎步骤、提交、Windows 自启动、隐私同意 |
| 数据位置 | `Infrastructure/DataLocationResolver.cs` | 解析数据根 |
| CLI | `Infrastructure/Commands.cs` | `plugin install/update`、`desktop exit`、写 result JSON |
| 视图 | `Views/*` | Splash / OOBE / 错误 / 加载详情 / 多实例提示 / 迁移提示 / 数据位置提示 |
| 协调 IPC | `Ipc/LauncherCoordinatorIpcServer.cs` | 第二实例附着到活动协调器 |
| AirApp 安装（CLI） | `AirApps/AirAppInstallerService.cs`、`AirApps/AirAppUpgradeQueueService.cs` | 命令行安装/升级 AirApp 包 |

**边界**：启动器里唯一的"更新"代码是 AirApp 包的升级队列（CLI `plugin update`）。**应用自身的更新不在启动器**，在宿主与安装器侧（PLONDS / `DeploymentMaintenance`）；启动器只做旧部署清理。

## 2. 启动管线

`LaunchPipeline` 顺序执行 5 个阶段，任一阶段返回 `Completed` 即短路，后续阶段不执行：

| 序 | 阶段 | 职责 |
|---|---|---|
| 1 | `CleanupDeploymentsPhase` | 清理旧部署；把 OOBE 判定覆盖进上下文 |
| 2 | `ExistingHostProbePhase` | 探测已有宿主；命中则按多实例行为处理并以 `ActivationRedirected` 结束 |
| 3 | `OobeGatePhase` | 需要时跑 OOBE 交互（先隐藏 Splash，完成后恢复） |
| 4 | `LaunchHostPhase` | 预启动 Runtime、定位并启动宿主、等 500ms 判断是否立即退出 |
| 5 | `MonitorStartupPhase` | 进入 `HostStartupMonitor` 循环，等成功判据 / 失败 / 超时 |

**顺序很关键**：`CleanupDeployments` 与 `ExistingHostProbe` 都在 OOBE 与启动之前——
即"先清理、再看有没有活着的宿主、再问用户、最后才启动"。

## 3. OOBE 与 Splash

- **Splash 先出现**：Splash 在 `App.OnFrameworkInitializationCompleted` 里创建并 `Show`，**早于管线运行**。
- **OOBE 判定**在 `LauncherOrchestrator.RunAsync` 开头先跑一次（用于决定 Splash 形态），随后 `CleanupDeploymentsPhase` 再把它覆盖进上下文。
- **交互发生在 `OobeGatePhase`**：先 `HideSplash` → 跑 `IOobeStep` → `ShowSplash`。所以"OOBE 在 Splash 之前"是错觉。
- **判定规则**（`OobeStateService`）：debug-preview / maintenance 抑制；存在 `oobe-state.json` 则跳过；否则按首次运行显示。
- **提交落点**（`OobeSessionCommitService.Commit`）依次：写数据位置 → 合并宿主 settings → 写 Windows 自启动 → 写隐私同意 → `MarkCompleted`。
- **标记文件**：`{数据根}/Launcher/state/oobe-state.json`。兼容读取旧路径 `.launcher/state/oobe-state.json` 与旧键 `first_run_completed`，读到后迁移并删除旧标记。
- **取消或保存失败**：中止启动，返回 OOBE 结果，不进入宿主启动。

## 4. 部署目录与标记

目录命名 `app-{version}-{index}`，index 自增到不重名。**版本解析取目录名按 `-` 切分后的第 2 段**，因此版本号本身不能含 `-`。

三个标记的**读写方**必须分清，这是这一节最容易搞错的地方：

| 标记 | 启动器 | 其他写入方 |
|---|---|---|
| `.current` | **只读**（过滤与排序、`HasCurrent`） | `DeploymentCommit.Activate`（安装器 / 宿主 PLONDS 安装路径） |
| `.partial` | **只读**（经 `DeploymentStaging.IsPartial`） | `DeploymentStaging.Prepare/MarkPartial` |
| `.destroy` | **唯一读写的标记**：清理时写入待删标记；保留项则删除该标记 | — |

**候选判据**（`DeploymentLocator`）：顶层目录、非 `.destroy`、非 `.partial`、**且目录内存在宿主可执行文件**。
**排序**：`.current` 优先，其次版本号降序。
**清理策略**：始终保留当前版本 + 最近 3 个有效版本 + 带快照的版本；其余标 `.destroy` 并尝试删除。

`DeploymentLayout` 还导出可执行文件名相关常量与 `GetHostExecutableName()` / `GetLauncherExecutableName()`；安装器与启动器都必须引用它，禁止各自硬编码标记名或前缀。

## 5. 启动宿主

1. **预启动 AirAppRuntime**，再启动宿主。
2. **定位宿主 exe** 的优先级：显式 `--app-root` → 已发布/便携位置 → 调试路径 → legacy 回退。
3. **启动方式**：Windows 下优先 Direct（Direct 才带参数、环境变量与 stderr 重定向），失败回退 ShellExecute。
4. **转发给宿主的参数**：原样转发 `RawArgs`（剥掉启动器专用项与命令词），再追加 `--LMD_PACKAGE_ROOT=`、`--LMD_VERSION=`、`--LMD_CODENAME=`、`--data-root=`。
5. **环境变量**同样注入 `LMD_PACKAGE_ROOT` / `LMD_VERSION` / `LMD_CODENAME` / `LMD_DATA_ROOT`。
6. 启动后**等 500ms** 判断进程是否立即退出（拿到早期失败的 stderr）。

不转发给宿主的项由 `HostLaunchPlan.LauncherOnlyOptions` 显式列出——新增启动器选项时要记得判断它是否该被剥离。

## 6. 成功判定与监控

**成功判据**（`StartupSuccessTracker.TryResolve`）：

| 情形 | 结论 |
|---|---|
| `ActivationRedirected` | 直接成功 |
| `DesktopVisible` / `Ready` | 直接成功 |
| 成功策略 `RestartTray` | 需要 `TrayReady` + `BackgroundReady` |
| 成功策略 `RestartBackground` | 需要 `BackgroundReady` |

另一条判据来自公共 IPC 的 `PublicShellStatus`（`DesktopVisible` / `MainWindowVisible` / `MainWindowOpened`）。

**超时**：软超时 45s、硬超时 180s。
**监控循环**（`HostStartupMonitor`）同时等：成功 TCS、激活失败 TCS、进程退出、定时检查点。

**状态持久化**（`StartupAttemptRegistry`）本身**不判成功**，只记状态与存活；成功/失败由 `MarkOwnedSucceeded` / `MarkOwnedFailed` 落库。它用 state 文件 + **命名互斥锁**，并做陈旧条目清理。

进程活着但阶段没到，会按情况给出 `shell_not_ready` / `ipc_connection_failed` / `desktop_not_visible` 一类结果码。

## 7. 已有实例与激活

- 启动前先探已有宿主（仅 `launch` 命令、非预览/维护、非 restart）。
- **探测方式**：连公共 IPC 调 `GetShellStatusAsync`，就绪判据是 `PublicIpcReady && ProcessId > 0`。
- **多实例行为**由设置决定：静默打开 / 提示后打开 / 仅提示 / 重启宿主。
- 命中已有实例时记为 `ActivationRedirected`、`MarkOwnedSucceeded`，随后关窗结束。
- 若宿主以退出码 12（`SecondaryActivationSucceeded`）退出，同样判成功 `activation_redirected`（见 `HostExitCodes`）。
- **第二启动器实例**：登记协调器失败时，附着到活动协调器并发送 `ActivateDesktop` / `Attach` 请求，而不是自己再拉一个宿主。

---

## 8. 失败处理

- **不做版本回滚**。`LauncherResult.RolledBackTo` 字段只被透传，**没有任何写入点**——不要据此认为回滚存在。
- 失败后弹错误窗，按用户选择：Exit / Retry（重建 Splash 再跑一遍管线）/ ActivateExisting。
- 部分失败码**不再重试**：`host_not_found`，或失败阶段不是 launch / launchHost 时直接退出。
- 激活类失败会先尝试用已存在宿主恢复，失败才判失败。

## 9. 与 AirAppRuntime 的交接

`Shell/AirAppRuntimeBridge.cs` 的两个动作：

| 方法 | 行为 | 失败表现 |
|---|---|---|
| `EnsureStartedAsync` | 先查 Runtime 状态；不可用则起进程，最多轮询 IPC 8 次，退避 `250ms × attempt` | 返回 `Available=false`（如 `process_not_created` / `runtime_unavailable`），**不抛异常** |
| `AttachHostAsync` | 校验 `pid > 0`；最多 4 轮，每轮先 `EnsureStartedAsync` 再 `AttachHostAsync(hostPid)` | 返回 `host_attach_failed` / `host_attach_unconfirmed`，**不抛异常** |

- 交接确认判据：`Accepted && Status.HostProcessId == hostPid && Status.HostProcessAlive`。
- `EnsureStartedAsync` 在**启动宿主路径**上，失败只记 Warn（"Host fallback remains available"）——宿主会按需自己拉起 Runtime，所以这里失败不致命。
- `AttachHostAsync` 在**协调器的成功分支、管线之外**执行；`hostPid` 取自结果 details（`hostPid` → `existingHostPid` → owned attempt）。交接失败只写 details 并告警，**不影响启动器判定为成功**。

---

## 10. 自启动与自更新

- 自启动：`LauncherWindowsStartupService` 写 HKCU `Run` 项 `LanMountainDesktop`，指向本 Launcher 进程。
- 写入时机：OOBE 提交时按用户选择设置。
- 启动器**没有应用自更新**；CLI 里的"更新"只针对 AirApp 包。

## 11. 命令行接口

**命令词**（`CommandContext`）：

| 命令 | 用途 |
|---|---|
| `launch`（默认） | 正常启动 |
| `preview-splash` / `preview-error` / `preview-oobe` / `preview-debug` | GUI 预览 |
| `plugin install` / `plugin update` | AirApp 包安装/升级（历史命令词） |
| `desktop exit` | 请求宿主退出 |

**选项**：`--debug`、`--show-loading-details`、`--app-root`、`--data-root`、`--launch-source`、`--restart-presentation`、`--source`、`--plugins-dir`、`--result`。

解析统一在 `CommandContext.ParseOptions`，支持 `--k=v`、`--k v` 与裸开关三种写法。

**没有 `--version` 开关**：全仓命令表里没有 version 命令，任何文档里出现的 `Launcher.exe --version ...` 都是错的。
