# 组件系统

桌面组件是宿主最核心的可视能力。本文讲**从定义到画在网格上**的完整链路，以及布局怎么持久化。轻应用作者视角的用法见 [组件系统](../01-AirApp开发/02-核心概念/02-组件系统.md)。

代码位置：`desktop/LanMountainDesktop/ComponentSystem/`（定义与注册）、`Views/Components/`（运行时）、`Services/`（工厂与布局持久化）。

最后核对：2026-11-14。

---

## 1. 先分清：两套组件面

这是本节最容易出错的地方——仓库里有**两套并存**的组件承载面，它们的布局持久化落在不同地方：

| 面 | 承载 | 布局服务 | 落盘 |
|---|---|---|---|
| 桌面网格 | 主窗口 `MainWindow` | `DesktopLayoutSettingsService` → `IComponentLayoutStore` | SQLite `component-state.db` |
| Windows 桌面板 | `DesktopPanelManagerService` | `DesktopPanelLayoutService` | `desktop_panel_layout.json` |

改组件行为时先确认改的是哪一面。文档里"布局存在哪里"这类问题必须指名是哪一个，否则答案一定是错的。

## 2. 定义层

```
ComponentRegistry.CreateDefault()                 ← 内置组件
  .RegisterExtensions(JsonComponentExtensionProvider.LoadProvidersFromDirectory(...))
  .RegisterComponents(<AirApp 贡献的定义>)
```

| 类型 | 位置 | 职责 |
|---|---|---|
| `ComponentRegistry` | `ComponentSystem/ComponentRegistry.cs` | 定义注册与查找（`CreateDefault` / `RegisterExtensions` / `RegisterComponents`） |
| `DesktopComponentDefinition` | `ComponentSystem/DesktopComponentDefinition.cs` | 定义记录：`Id`、`DisplayName`、`IconKey`、`Category`、最小/最大格数、`AllowStatusBarPlacement` / `AllowDesktopPlacement`、`ResizeMode` |
| `IComponentExtensionProvider` | `ComponentSystem/Extensions/` | 外部定义来源的抽象 |
| `JsonComponentExtensionProvider` | `ComponentSystem/Extensions/JsonComponentExtensionProvider.cs` | JSON 扩展解析 |

**JSON 组件扩展**：目录 `<BaseDirectory>/Extensions/Components`，只读**顶层** `*.json`；文件是数组，元素字段为 `Id` / `DisplayName` / `IconKey` / `Category` / `MinWidthCells` / `MinHeightCells` / `AllowStatusBarPlacement` / `AllowDesktopPlacement` / `Description` 等。

**装配入口**是 `Services/DesktopComponentRegistryFactory.cs`：

- `Create(airAppRuntimeService)` → 定义注册表（内置 + JSON 扩展 + 轻应用定义）
- `CreateRuntimeRegistry(...)` → 运行时注册表（控件工厂 + 圆角策略）

轻应用定义与内置/扩展定义重名时**跳过轻应用那个**并写 `Debug.WriteLine`，不抛异常。

## 3. 运行时层

| 类型 | 位置 | 职责 |
|---|---|---|
| `DesktopComponentRuntimeRegistration` | `Views/Components/DesktopComponentRuntimeRegistry.cs` | 一条运行时注册：控件工厂 + 圆角解析 |
| `DesktopComponentRuntimeRegistry` | 同上 | 按 `ComponentId` 解析注册；`CreateControl` 负责实例化与注入 |
| `DesktopGridLayoutService` | `Services/DesktopGridLayoutService.cs` | 网格几何：列/行/单元尺寸/间距 |
| `DesktopComponentRuntimeContext` | `ComponentSystem/` | 运行时上下文 |

`CreateControl` 在创建控件时会依次补齐：

- 设置上下文（`IComponentSettingsContextAware`）
- 运行时上下文（`IComponentRuntimeContextAware`）
- 放置上下文（`IComponentPlacementContextAware`）——`ComponentId` + `PlacementId`
- 外观/圆角上下文（`IComponentChromeContextAware`）
- 网格单元尺寸

这些 `IComponent*Aware` 接口是"宿主把运行期信息交给控件"的正规通道。控件实现哪个接口就拿到哪一份上下文——**不要指望构造函数注入这些**，它们是放置期才存在的。

## 4. 布局与持久化（桌面网格）

```
MainWindow
  → DesktopLayoutSettingsService.Load() / Save()
      → IComponentLayoutStore = ComponentDomainStorageProvider.Instance
          → SqliteComponentDomainStorage
              文件：component-state.db
              表：component_layout / component_placement
```

快照模型：

| 类型 | 内容 |
|---|---|
| `DesktopLayoutSettingsSnapshot` | 页数、当前面、放置列表 |
| `DesktopComponentPlacementSnapshot` | `PlacementId`、`PageIndex`、`ComponentId`、`Row`、`Column`、`WidthCells`、`HeightCells` |

**旧 JSON 一次性迁移**：标记 `component_domain_v1`，源文件 `desktop-layout-settings.json` / `component-settings.json`；迁移完成后不再读旧文件。

**桌面板是另一套**：`DesktopPanelLayoutService`，文件 `desktop_panel_layout.json`，旧名 `fused_desktop_layout.json`（含旧字段导入逻辑）。

## 5. 组件库与拖放

| 类型 | 位置 | 职责 |
|---|---|---|
| `ComponentLibraryService` | `Services/ComponentLibraryServices.cs` | 组件库数据（定义 + 运行时注册表） |
| `EmbeddedComponentLibraryService` | 同上 | 主窗口内嵌形态 |
| `DesktopPanelComponentLibraryWindow` | `Views/` | 宿主级组件库窗口 |
| `DesktopEditSession` | `DesktopEditing/DesktopEditSession.cs` | 拖放/编辑的会话状态 |

`DesktopEditSession` 的状态机是拖放的真相：`PendingNew` → `DraggingNew` / `DraggingExisting` / `ResizingExisting`。落格提交与编辑模式的进入/退出分散在 `Views/MainWindow.ComponentSystem.cs` 与 `Services/DesktopPanelManagerService.cs`——**目前没有单一入口**，改拖放行为需要在这两处一起看。

## 6. 组件编辑器

```
MainWindow.OpenSelectedComponentEditor
  → ComponentEditorWindowService.Open(ComponentEditorOpenRequest(...))
      → DesktopComponentEditorRegistry（按组件 Id 找编辑器工厂/首选尺寸/缩放比）
```

- 窗口服务：`Services/ComponentEditorWindowService.cs`（单窗口复用、材质主题、宿主上下文）
- 注册表：`ComponentSystem/DesktopComponentEditorRegistry.cs`
- 装配：`Services/DesktopComponentEditorRegistryFactory.cs`（内置编辑器 + 轻应用编辑器）
- 视图基类：`Views/ComponentEditors/` 下的 `ComponentEditorViewBase` 与各 `XxxComponentEditor`

轻应用通过 `AddAirAppComponentEditor<TControl>` 贡献编辑器，落点就是这里。

## 7. 视觉与圆角约束

- 组件根容器**必须且仅能**用 `{DynamicResource DesignCornerRadiusComponent}`；内部元素按层级用 `DesignCornerRadiusSm/Md/Lg`。
- Token 数值随主题档位变化（`Styles/GlassModule.axaml`），**不要在代码或文档里写死像素值**。
- 严禁对圆角资源乘 `scale`——缩放在全局样式里统一控制。
- 细节见 [视觉规范](../03-组件设计规范/02-视觉规范.md)。

## 8. 已知薄弱点

| 项 | 说明 |
|---|---|
| 两套组件面 | 布局持久化、编辑模式、清理逻辑各一套；改动容易只覆盖一侧 |
| 拖放入口未收口 | 落格提交与编辑模式切换分散在 `MainWindow.ComponentSystem.cs` 与 `DesktopPanelManagerService.cs` |
| 布局存储从 JSON 迁到 SQLite | 迁移标记 `component_domain_v1` 之后旧 JSON 不再读；排查"布局丢了"要先确认标记状态 |
| 轻应用编辑器无机器闸门 | 未找到专门钉 `DesktopComponentEditorRegistry` 的测试类，改动风险靠人工 |
| **引用了未定义的资源键** | `Views/Components/CnrDailyNewsWidget.axaml` 使用 `{DynamicResource CardBackgroundBrush}` / `CardBorderBrush` / `CardBackgroundSecondaryBrush` / `CardBackgroundHoverBrush` / `CardBackgroundPressedBrush`，而全仓**没有任何 `x:Key` 定义它们**。`DynamicResource` 取不到值不报错，症状是该组件**没有背景与边框**（静默失色）。真实键名见 [设计 Token 与资源真源](../03-组件设计规范/00-设计token真源.md) |
