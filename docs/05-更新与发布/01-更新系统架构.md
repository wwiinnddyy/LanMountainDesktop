# 更新系统架构

阑山桌面的应用更新基于 **PLONDS**（Penguin Logistics Online Network Distribution System）实现：把新版本发布成"版本目录 + 清单 + 增量包"，宿主负责检查与准备，**落盘切换由 `core/LanMountainDesktop.Core/Deployment/` 的部署原语完成**，启动器只做版本选择与旧版本清理。

- 增量算法细节：[增量更新实现](02-增量更新实现.md)
- 打包产物：[打包与构建](03-打包与构建.md)
- 流水线：[CI/CD 配置](04-CICD配置.md) · [发布流程](05-发布流程.md)

最后核对：2026-11-14。

> **读前必看**：本文替代了旧版。旧版把 `UpdateOrchestrator` 写成更新编排真源、把清单叫 `plonds-filemap.json`、把签名说成主流程必经——这些都与当前代码不符。若你在别处看到那些说法，以本文为准。

---

## 1. 参与者与真实入口

```
设置界面
  → UpdateSettingsService（宿主，更新能力的唯一入口）
       IsPlondsSelected() ── 目前硬编码 true ──┐
                                              ↓
                            PLONDS 主路径（Check → Prepare → Install → Activate）
                            GitHub/UpdateOrchestrator 旁路（保留但不会被选中）
```

| 参与方 | 位置 | 职责 |
|---|---|---|
| `UpdateSettingsService` | `desktop/LanMountainDesktop/Services/Settings/SettingsDomainServices.cs` | 检查、下载、安装、回滚的编排 |
| `PlondsService` | `Services/Plonds/PlondsService.cs` | 取清单、判有无更新 |
| `PlondsManifestSelector` | `Services/Plonds/PlondsManifestSelector.cs` | 按平台与频道筛选候选 |
| `PlondsDownloadPlanner` | `Services/Plonds/PlondsDownloadPlanner.cs` | 决定增量还是完整 |
| `PlondsHttpPackageDownloader` | `Services/Plonds/PlondsHttpPackageDownloader.cs` | 下载 + 校验 + 解压到 staging |
| `PlondsPreparedPackageInstaller` | `Services/Plonds/PlondsPreparedPackageInstaller.cs` | 全量/增量安装到新部署目录 |
| `PlondsMaintenanceGateway` | `Services/Plonds/PlondsMaintenanceGateway.cs` | 需要动根目录时交给维护程序 |
| 部署原语 | `core/LanMountainDesktop.Core/Deployment/` | `DeploymentStaging` / `DeploymentCommit` / `DeploymentLocator` / `DeploymentMaintenance` |
| 启动器 | `desktop/LanMountainDesktop.Launcher/` | 版本选择、旧部署清理、启动协调 |

**`UpdateOrchestrator` 与 GitHub 通道仍在代码里，但已不是主路径**：`IsPlondsSelected()` 直接返回 `true`，`IsGitHubSelected()` 返回 `false`。这意味着 GitHub 那条链上的修复不会影响用户——排查更新问题时必须先确认走的是哪条。

## 2. 清单（PLONDS.json）

**清单文件名是 `PLONDS.json`**（`plonds-filemap.json` 是宿主早期遗留名，只在少数兼容路径出现）。

来源（内置真源，可被环境变量覆盖）：

| 优先级 | 来源 | 地址形态 |
|---|---|---|
| 100 | S3/CDN | `https://<cdn>/lmdesktop/lanmountain/update/plonds/{platform}/{channel}/PLONDS.json` |
| 50 | GitHub Releases API | `releases?per_page=50`，取资产 `PLONDS-{platform}.json`（windows-x64 找不到时回退 `PLONDS.json`） |

字段（服务端与客户端共用模型，序列化为 **camelCase**）：

| 字段 | 含义 |
|---|---|
| `formatVersion` | 清单格式版本 |
| `currentVersion` | 清单描述的版本 |
| `previousVersion` | **增量基线**：增量包只能从这一版升上来 |
| `isFullUpdate` | 是否为完整更新 |
| `requiresCleanInstall` | 是否必须走完整安装程序（见第 5 节） |
| `channel` / `platform` | 频道与平台（如 `stable` / `windows-x64`） |
| `updatedAt` | 生成时间 |
| `filesMap` | 路径 → `{action, hash, size, hashAlgorithm}` |
| `changedFilesMap` | 增量包内文件 → `{archivePath, hash, size, hashAlgorithm}` |
| `checksums` | 包校验值，形如 `md5:<hex>` / `sha256:<hex>` |
| `downloads` | `github{releaseUrl, manifestUrl, changedZipUrl, filesZipUrl}` 与 `s3{bucket, prefix, manifestKey/Url, changedZipKey/Url, filesZipKey/Url, ...}` |
| `sources` | 来源列表 |

宿主对旧/多写法有容忍（`PlondsManifestParser`）：`op|action`、`contentHash|sha256|fileSha256`、`objectPath|archivePath`、以及 `hash{algorithm,value,bytes}`。**写清单生成器时不要依赖这种容忍**——它是为历史包袱存在的。

## 3. 检查与选择

```
CheckAsync
  → PlondsService.FindLatestAsync    取清单
  → PlondsManifestSelector           过滤：Platform 必须相等；Channel 相等（preview 额外接受 stable）
                                     再按版本降序取最高
  → CompareTo > 0                    清单 currentVersion vs 当前进程版本
```

当前版本取自 `AppVersionProvider.ResolveForCurrentProcess().Version`。

**增量 vs 完整的判据**（`PlondsDownloadPlanner`）——满足任一即走完整包：

- 用户显式要求完整包
- **基线不匹配**：`manifest.previousVersion != 当前版本`
- `requiresCleanInstall`
- `isFullUpdate`

否则先试增量，失败再回退完整。**基线不匹配这条是最容易被忽略的**：跳版本升级（1.0 → 1.5 而清单基线是 1.2）必然走完整包。

## 4. 安装与激活

### 4.1 PLONDS 包路径（主路径）

```
PlondsHttpPackageDownloader.PrepareAsync
  下载 Files.zip / changed.zip → PlondsVerifier 按 Checksums 校验 zip → 解压到 staging
        ↓
PlondsPreparedPackageInstaller
  全量：校验 FilesMap → 复制到新 app-{version}-{index} → 再次校验 → 激活
  增量：先把当前部署整目录复制到新目录 → 按 FilesMap 覆盖 add/replace、删除 delete、跳过 reuse → 校验
        ↓
DeploymentCommit.Activate
  写新目录 .current → 删旧 .current → 清 .partial/.destroy → 落快照（崩溃时能回退标记）
```

### 4.2 根目录维护路径

Launcher / Runtime 这类**根目录文件**发生变化时，PLONDS 包无法就地替换（它们不在版本目录里）。此时返回 `requires_clean_install`，改由 **NativeAOT 维护程序**处理（`DeploymentMaintenance.ExecutableName`，即 `LanDesktopPLONDS.installer.exe` 的 `--apply-update` 入口）。

### 4.3 完整安装程序回退

`DownloadPlondsCleanInstallAsync` 从 GitHub Release 取 EXE，写 `deployment.lock`，再由 `UpdateInstallGateway` 启动安装器。

**`deployment.lock` 的真实字段**（不是旧文档写的 `FromVersion/FileMapPath/SignaturePath/ArchivePath`）：

| 字段 | 含义 |
|---|---|
| `SchemaVersion` | 锁文件格式版本 |
| `Kind` | 部署种类（如完整安装） |
| `TargetVersion` | 目标版本 |
| `PayloadPath` | 载荷路径 |
| `PayloadSha256` | 载荷哈希 |
| `CreatedAtUtc` | 创建时间 |

## 5. 标记文件与目录布局

```
安装根/
├── LanMountainDesktop.Launcher.exe
├── LanMountainDesktop.AirAppRuntime.exe
├── LanDesktopPLONDS.installer.exe        # 在线安装器 / 维护程序（同一 exe）
├── app-{version}-{index}/                # 每个版本一个部署目录
│   ├── .current                          # 当前活动部署标记
│   ├── .partial                          # 写入未完成标记
│   └── .destroy                          # 待清理标记
└── .Launcher/
    ├── state/oobe-state.json
    ├── snapshots/{guid}.json             # 更新快照（注意：不在 update/ 下，也没有 snapshot- 前缀）
    ├── update/
    │   ├── incoming/                     # 下载缓存与对象文件
    │   └── public-key.pem                # 签名公钥（仅 delta 应用路径使用）
    └── logs/
```

| 标记 | 写入方 | 语义 |
|---|---|---|
| `.current` | `DeploymentCommit.Activate` | 当前活动部署；启动器只读 |
| `.partial` | `DeploymentStaging.Prepare/MarkPartial` | **写入期**标记（不是"下载中"——下载缓存在 `.Launcher/update/incoming`） |
| `.destroy` | `DeploymentActivator.Activate`（delta 应用）与启动器清理逻辑 | 待删除；**启动器是唯一会删它的地方** |

命名规则：`app-{version}-{index}`，index 自增避免重名；**版本号本身不能含 `-`**，因为解析取目录名按 `-` 切分的第 2 段。

## 6. 版本选择（启动器侧）

启动器用 `DeploymentLocator.FindCurrentDeploymentDirectory` / `FindBestDeploymentHost`：

- 只扫顶层 `app-*` 目录
- 过滤掉 `.destroy`、`.partial`，**且目录内必须存在主程序可执行文件**
- `.current` 优先，其次版本号降序

旧版本清理（`CleanupDeploymentsPhase`）：保留当前版本 + 最近若干个有效版本 + 带快照的版本，其余标 `.destroy` 并尝试删除。

## 7. 回滚

```
设置 → 回滚
  → RollbackPlondsAsync
       存在 .root-backup  → 派维护程序恢复根目录
       否则               → UpdateRollbackGateway.RollbackLatest
```

**只有"回退到最新快照"这一种能力**，没有旧文档描述的"版本历史列表"。原因是更新过程本身就会保留旧部署目录（新版本写在新目录、旧目录的 `.current` 被移除但目录还在），所以现实中的回退大多靠启动器选回旧目录。

## 8. 安全机制（现状）

分清两条路径，它们的强度完全不同：

| 路径 | 校验 |
|---|---|
| **PLONDS 包（主路径）** | 清单 `checksums`（md5/sha256）校验 zip + 落地逐文件哈希校验（`PlondsVerifier` / `VerifyFiles`） |
| delta 应用路径（非主流程） | `plonds-filemap.json` + `.sig` 的 **RSA PKCS1-SHA256** 验签，公钥在 `{launcherRoot}/.Launcher/update/public-key.pem`；缺签名或缺公钥即失败 |

也就是说：**"RSA 签名确保安全"这条对主流程不成立**——主流程靠哈希校验，不验签。这点必须写清楚，否则会高估更新链的防护。

其他相关事实：

- 安装器清单签名 `ManifestSignatureVerifier` 用的是 **RSA-PSS-SHA256**（不是 Ed25519），而且**在生产路径上没有调用点**；公钥为空时跳过并放行。
- Authenticode 默认**只报告**，`LANMOUNTAIN_INSTALLER_REQUIRE_SIGNED=1` 才强制。
- 下载的 .NET 运行时安装器必须是 Microsoft 签名，否则拒绝。
- 路径遍历防护统一走 `PathContainment`（不用裸前缀比较），宿主编排、安装器、包解压都调用。
- **CI 里没有任何代码签名步骤**（无 signtool、无签名脚本调用）。

`docs/INSTALLER_SECURITY.md` 里 Ed25519 的说法与代码不符（代码注释明确说明 .NET 10 不把 Ed25519 作为独立类型暴露，因此改用 RSA-PSS-SHA256）——该文档已按此修正。

## 9. 频道

| 频道 | 过滤规则 |
|---|---|
| stable | 只取 `channel = stable` |
| preview | 取 `stable` + `preview` |

过滤依据是**清单的 `channel` 字段**，不是 GitHub Release 的 `prerelease` 标记（后者只在被旁路的 GitHub 通道里用到）。

## 10. 已知问题与坑

| 项 | 说明 |
|---|---|
| 两条更新链路并存 | `IsPlondsSelected()` 硬编码 `true`，GitHub/`UpdateOrchestrator` 那条是死路径；改动或排查都要先确认落点 |
| "增量"名不副实 | 安装器的 `UpdateIncrementalAsync` 仍会**下载完整 zip**，只是从当前部署复制未变文件、仅从 zip 抽变更文件（见 [增量更新实现](02-增量更新实现.md)） |
| 主流程不验签 | 见第 8 节 |
| 两个打包脚本已失效 | `scripts/Sign-FileMap.ps1`、`scripts/Generate-PlondsArtifacts.ps1` 调用的 `Plonds.Tool sign` / `generate` **子命令不存在**，运行会以 "Unknown command" 失败；且无 workflow 引用 |
| 文档漂移 | 旧版本文档（含 `docs/audits/2026-10-07-update-chain.md`）记录的结论多数已被代码演进覆盖，不要直接当现状引用 |
