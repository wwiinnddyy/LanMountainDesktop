# 增量更新实现

本文讲**增量到底增在哪**：包是怎么差出来的、宿主怎么应用、以及哪些地方名不副实。

- 清单字段与整体流程：[更新系统架构](01-更新系统架构.md)
- 生成增量的工具链：[发布流程](05-发布流程.md)

最后核对：2026-11-14。

---

## 1. 一句话结论

**增量是文件级的，不是二进制补丁。** 动作集合只有四个：`add` / `replace` / `reuse` / `delete`（`Plonds.Shared/PlondsConstants.cs`）。全仓没有 bspatch / block map 一类的二进制差分代码。

---

## 2. 差量怎么算出来

服务端（`PenguinLogisticsOnlineNetworkDistributionSystem`）有两种算法，都由 CI 选择：

### 2.1 `file-compare`

解压新旧两个 payload zip，按路径比对 SHA256/MD5：

| 比对结果 | 动作 |
|---|---|
| 内容相同 | `reuse` |
| 内容不同 | `replace` |
| 新增路径 | `add` |
| 新版本里消失 | `delete` |

只把 `add` / `replace` 的文件打进 `changed.zip`。实现见 `Plonds.Core/Publishing/PlondsDeltaBuilder.cs`。

### 2.2 `build-delta-from-commits`

`git diff --name-only baseline..current` 取**源文件**变更，再按一张写死的「源目录 → 产物」映射（例如 `desktop/LanMountainDesktop` → `LanMountainDesktop.dll/.exe`）换算成产物文件，把对应产物打进 `changed.zip`。无变更时回退到 `file-compare`。实现见 `PlondsCommitDeltaBuilder.cs`。

**映射表是这份算法的单点风险**：新增一个产物（比如新的辅助 exe）却忘了加映射，它就不会进增量包。

### 2.3 `requiresCleanInstall` 的由来

**Launcher 文件哈希变化**（或 commit 分析里含 Launcher 产物）时置位。原因见 [更新系统架构](01-更新系统架构.md) 第 4.2 节：Launcher 在根目录，增量包动不了它。

## 3. 包结构与校验

| 产物 | 内容 |
|---|---|
| `changed-windows-{arch}.zip` | 只含变更文件 |
| `Files.zip`（或 `files-windows-{arch}.zip`） | 完整载荷 |
| `PLONDS-windows-{arch}.json` | 清单；x64 另存通用 `PLONDS.json` |

清单里两组映射各管一段：

- `filesMap`：**目标部署**里每个文件的 `{action, hash, size, hashAlgorithm}`
- `changedFilesMap`：**增量包内**每个文件的 `{archivePath, hash, size, hashAlgorithm}`

`checksums` 形如 `md5:<hex>` / `sha256:<hex>`；构建器只写 `changed.zip` 的校验值，发布器补上 `Files.zip`。

## 4. 宿主怎么应用

```
PlondsHttpPackageDownloader.PrepareAsync
  解析 URL（清单 downloads.s3 优先，回退 downloads.github）
  → 下载 zip → PlondsVerifier 按 checksums 校验 → 解压到 staging
        ↓
PlondsPreparedPackageInstaller
  增量：当前部署整目录 → 复制到新 app-{version}-{index}
        → 按 filesMap：add/replace 写文件、delete 删文件、reuse 跳过
        → 逐文件哈希校验
  全量：校验 → 复制 → 再校验
        ↓
DeploymentCommit.Activate    写 .current、清标记、落快照
```

对象文件的取用有两条来源（`PlondsPayloadResolver`）：解压后的 `objects/…`，或 `changed` 目录；必要时 GZip 解压（`PlondsUpdateApplier`）。

**`delete` 的两种语义要分清**——这是最容易踩的坑：

| 位置 | 对 `delete` 的处理 |
|---|---|
| 宿主增量应用（PLONDS 包路径） | **跳过**（新目录是从旧目录复制来的，理论上不该有该文件） |
| 安装器增量（`IncrementalPlanBuilder` → `PlondsPreparedPackageInstaller`） | **删除目标文件** |

两者同名不同为。改任何一侧前先确认在说哪一条。

## 5. 三处"增量"名不副实的地方

| 说法 | 实情 |
|---|---|
| "安装器增量只下载变更文件" | `OnlineInstallService.UpdateIncrementalAsync` **仍下载完整 zip**，只是用 `IncrementalPlanBuilder` 从当前部署复制未变文件、仅从 zip 抽变更文件 |
| "增量用二进制补丁" | 不存在。动作集合只有四个文件级操作 |
| "宿主侧增量安装会验 RSA 签名" | 主流程只做 checksums + 逐文件哈希；RSA 验签只在非主流程的 delta 应用路径上 |

这三条都写进文档的原因是：它们会直接影响你对"更新有多安全、多省流量"的判断。

## 6. 失败与回退

| 失败点 | 表现 |
|---|---|
| 下载失败 | 换下一个来源；多来源用尽才报错 |
| zip 校验失败 | `PlondsVerifier` 拒收，staging 丢弃 |
| 逐文件哈希不符 | 安装失败，返回 `plonds_install_failed` |
| 需动根目录 | 返回 `requires_clean_install`，交维护程序 |
| 增量应用失败 | 回退到完整包路径 |

旧版本**不会因为失败被删除**：新版本写在新目录，旧目录只是被摘掉 `.current`。真正删旧目录的是启动器清理（`.destroy`）。
