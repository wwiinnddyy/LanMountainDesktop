# 发布流程

本文是一条**从改代码到用户能更新**的完整路径，按顺序列出每一步的实际动作与产物。

最后核对：2026-11-14。

---

## 0. 前置：确定版本号

版本真源是 **git tag**。发布前先确定 tag，形如 `v1.2.3`。

`Directory.Build.props` 里的 `0.0.0-dev` 是占位值，**不要手工改它来发布**——它会在构建期被覆盖。

如果本次涉及轻应用 SDK 的公开表面变化，还需要先递增 `AirAppSdkInfo.SdkVersion` / `ApiVersion` 与包版本（见 [AirApp 运行时](../04-架构与实现/04-AirApp运行时.md)），否则市场里的轻应用会出现"同名同一版本号但二进制不兼容"。

---

## 1. 打 tag 并推送到远端

```
git tag v1.2.3
git push origin v1.2.3
```

tag 匹配 `v*` 是 `release.yml` 的触发条件。

---

## 2. release.yml 的 prepare

从 tag 解析出：

- `version`（tag 去掉 `v`）
- 4 段 `assembly_version`
- 频道（stable / preview）

然后 `Set-ReleaseVersion.ps1` 把版本写进：

- `Directory.Build.props`
- 三个 csproj 的 `<Version>`
- 两个 `app.manifest` 的 `assemblyIdentity/@version`

最后构建期再用 `-p:Version` / `-p:AssemblyVersion` 统一注入。

---

## 3. 三平台构建与重组

Windows 侧按固定顺序发布，然后做目录重组（详见 [打包与构建](03-打包与构建.md) 第 2 节）：

```
Launcher(AOT) → 主程序 → AirAppRuntime → AirAppHost → 维护安装器(AOT)
→ 重组为 publish/windows-{arch}/（根放三个 exe，app-{version}/ 放主程序并写 .current）
→ 校验目录结构
→ 打 files-windows-{arch}.zip
```

Assemblies 版本注入与目录校验都在这一步，**目录校验失败即中止发布**——这是防"发出一个启动不了的包"的关键闸门。

---

## 4. 建 GitHub Release

`github-release` job 用 `release-action` 创建 Release，挂上安装包与载荷 zip，并**显式 dispatch `plonds-comparator.yml`**。

产物命名：

- 安装包 `LanMountainDesktop-Setup-{version}-{arch}.exe`
- 载荷 `files-windows-x64.zip` / `files-windows-x86.zip` / `files-linux-x64.zip`

**此时 Release 还不可供更新使用**——增量资产还没生成。

---

## 5. plonds-comparator 生成增量

对 x64 / x86 各跑一次差量构建（`build-delta` 或 `build-delta-from-commits`），产出：

- `changed-windows-{arch}.zip`
- `PLONDS-windows-{arch}.json`
- x64 另存通用名 `changed.zip` / `PLONDS.json`

上传到同一个 Release，末段显式触发 `plonds-uploader.yml`。

---

## 6. plonds-uploader 发布清单与包

先 `enrich-manifest --write-legacy-copy` 发 GitHub 通道，再 `publish-s3` 上 S3。

S3 上的目录规则：

```
{prefix}/{version}/PLONDS.json
{prefix}/{version}/changed.zip
{prefix}/{version}/Files.zip
{prefix}/{version}-changed/    （展开目录）
{prefix}/{version}-Files/      （展开目录）
{prefix}/PLONDS.json           （latest 指针）
```

**latest 指针只在版本不倒退时提升**——这是一条防"把 latest 指到旧版本"的保护，不要绕过它。

**S3 步骤是 `continue-on-error: true`**：上传失败不会让这次运行变红。发布者有责任单独确认 S3 侧真的成功了，否则用户拿到的还是旧清单。

---

## 7. 验收

发布完成的判据（按顺序确认）：

| 检查 | 期望 |
|---|---|
| Release 资产 | 安装包 + `files-*.zip` + `changed-*.zip` + `PLONDS*.json` 都在 |
| `PLONDS.json` 的 `currentVersion` | 等于本次 tag 版本 |
| `PLONDS.json` 的 `previousVersion` | 是**上一个已发布版本**（决定谁能走增量；跳版本的用户会走完整包） |
| `requiresCleanInstall` | 本次是否动了 Launcher / 根目录？是则为 `true` |
| S3 latest 指针 | 已指向新版本 |
| 频道 | 与 tag 预期一致（preview 不会把 stable 用户拉过去） |

端到端验收**必须在有网络的环境上做**：本地无法验证 S3 可下载性与清单可解析性。仓库内的更新链测试（`UpdateChainRegressionTests` 等）只覆盖逻辑，不覆盖线上分发。

---

## 8. 发完之后

- **轻应用市场**（兄弟仓 `LanAirApp`）如果需要跟随，另行提交 `registry/official-airapps.json`，`index.json` 由那边的 CI 生成。
- **轻应用 SDK** 的 NuGet 发布由 `airapp-sdk-publish.yml` 负责。
- 若发现发布错误：**不要改历史**，走新提交 + 新 tag。

---

## 9. 常见发布事故

| 症状 | 常见原因 |
|---|---|
| 用户收不到更新 | S3 上传静默失败（`continue-on-error` 吞掉了）；或 latest 指针没提升 |
| 用户更新后要求重新安装 | `requiresCleanInstall=true` 本应如此；若不该为真，检查是否动了 Launcher 或映射表 |
| 更新的都是完整包 | 清单 `previousVersion` 与用户当前版本不匹配（跳版本） |
| 更新后启动失败 | 目录重组或目录校验被绕过；回退靠启动器选回旧部署目录 |
| 增量包内容不全 | `build-delta-from-commits` 的「源目录 → 产物」映射漏了新产物 |
