# 轻应用生命周期

## 发现

宿主启动时扫描轻应用目录（`<数据根>\Extensions\AirApps`），按这个顺序收集候选：

1. 递归扫描 `*.laapp` 包，读取包内唯一的 `airapp.json`
2. 递归扫描散放的 `airapp.json`
3. `--dev-airapp` / `LMD_DEV_AIRAPP` 指定的开发期路径

`.runtime` 子目录是解包暂存区，不参与扫描。

候选按来源优先级排序：**开发期覆盖 > 散放清单 > `.laapp` 包**。
同一个 `id` 只保留优先级最高的一个，其余记为加载失败并写日志。
开发期覆盖是唯一不会因为「id 重复」而报错的来源。

## 清单校验

读取清单时 SDK 会做归一化与校验，任何一项不通过都会让这个轻应用加载失败：

- `id`、`name`、`entranceAssembly` 必须非空
- `apiVersion` 缺省时取宿主当前 API 版本
- `apiVersion` 必须可解析，且**主版本号必须等于宿主 SDK 的主版本号**
- `sharedContracts` 不能有重复的 `id@version`
- `runtime.mode` 必须是已知取值

主版本相等是硬门禁，没有向下兼容的宽限。宿主 API 是 `1.0.0` 时，
声明 `2.0.0` 或 `5.0.0` 的轻应用一律拒绝加载。

## 加载

每个轻应用装进一个**独立的、可回收的 `AssemblyLoadContext`**：

```
读取 airapp.json
   ↓
解析 entranceAssembly 绝对路径
   ↓
校验入口程序集旁存在 .deps.json     ← 缺失直接失败
   ↓
创建 AirAppLoadContext（含共享程序集白名单）
   ↓
加载入口程序集，反射查找 [AirAppEntrance] 类型
   ↓
实例化入口类
```

关于入口类型的两条硬规则：

- 程序集里必须有**恰好一个**实现 `IAirApp` 的具体类型；一个都没有会失败
- 有多个时，必须用 `[AirAppEntrance]` 指明其中一个，否则失败

共享程序集白名单的意义：SDK 本身、Avalonia 等由宿主统一提供，
不从轻应用的 `AssemblyLoadContext` 里重复加载。这就是工程里
必须写 `ExcludeAssets="runtime"` `PrivateAssets="all"` 的原因——
一旦把 SDK 程序集打进 `.laapp`，就会出现「同名类型不是同一个类型」的诡异错误。

## 初始化

```
IAirApp.Initialize(HostBuilderContext, IServiceCollection)
   ↓
宿主构建本轻应用的 ServiceProvider
   ↓
宿主从容器中读取各类注册：
   AirAppComponentRegistration / AirAppWindowRegistration
   AirAppSettingsSectionDefinition / AirAppServiceExportRegistration
   IHostedService / IAirAppPublicIpcContributor
   ↓
启动轻应用注册的 IHostedService
   ↓
IAirApp.OnStartedAsync(IAirAppRuntimeContext)
```

`Initialize` 是**唯一**的注册时机。它返回之后容器就构建完了，
再往 `IServiceCollection` 里加东西不会有任何效果。

`Initialize` 里不要做耗时操作：它在宿主启动路径上，
每个轻应用的耗时都会直接叠加到桌面可见时间上。文件读写、网络请求
放到 `OnStartedAsync` 或后台服务里。

## 运行

`OnStartedAsync` 拿到 `IAirAppRuntimeContext`，此时可用的能力：

- `Services`：本轻应用的服务容器
- `Logger`：写入宿主日志
- `MessageBus`：与其他轻应用通信
- `Appearance`：主题快照，并可订阅 `Changed` 事件
- `DataDirectory` / `CacheDirectory`：可写目录
- `OpenWindowAsync` / `CloseWindow`：窗口轻应用

组件控件不在这条链路上创建。宿主按用户在桌面上的放置情况，
在需要渲染时才通过 `AirAppComponentRegistration.ControlFactory` 创建控件实例，
每个放置位置一个实例。所以组件的构造函数可能被调用任意多次，也可能一次都不调用。

## 停止

宿主关闭时调用 `OnStoppingAsync`，随后停止轻应用注册的 `IHostedService`。

`OnStoppingAsync` 要快。宿主的关闭协调有时间预算，拖太久会被强制结束，
未落盘的数据就丢了。需要长时间清理的工作应当增量进行，而不是留到退出时。

## 窗口轻应用的独立生命周期

窗口不在上面这条进程内链路里。组件调用 `OpenWindowAsync` 后：

```
宿主 AirAppLauncherService 构造打开请求（带包路径）
   ↓ IPC
AirAppRuntime 进程：解析实例键，已存在则激活，否则启动新进程
   ↓
AirAppHost 进程：读取包内 airapp.json，解析 [AirAppEntrance]，
                 构造 IAirAppWindow，把 Content 嵌入窗口外壳
```

窗口进程与宿主进程**内存完全隔离**，窗口崩溃不会带倒桌面。
代价是组件和窗口之间不能共享内存对象，要通过 `DataDirectory` 或 IPC 交换数据。

`IAirAppWindow` 的回调顺序：
`OnWindowOpeningAsync` → `OnWindowOpened` → `OnWindowClosing` → `OnWindowClosed`。

## 关于 runtime.mode

清单里的 `runtime.mode` 目前只有 `in-proc`（同义写法 `in-process`）会被宿主执行。
`isolated-background` 与 `isolated-window` 是预留取值：写了能通过校验，
但不会改变加载行为——轻应用本体依然在宿主进程内加载。
真正的进程隔离目前只发生在**窗口**这条链路上，与 `runtime.mode` 无关。
